# PulseAudio/troubleshooting

## PulseAudio troubleshooting

Pulseaudio runtime info can be checked with one command:

`user $````
pa-info
```
It prints useful info about all modules loaded and any error can happen while module loading the bootstrap sequence. When there is an issue with PulseAudio, remember to check pa-info output to start troubleshooting.

The sound card might be muted. Start alsamixer, provided by [media-sound/alsa-utils](https://packages.gentoo.org/packages/media-sound/alsa-utils), and make sure each column has a green `00` under it (use the `m` key to toggle mute/unmute). Install [media-sound/pavucontrol](https://packages.gentoo.org/packages/media-sound/pavucontrol) and check if there is any output on the pavucontrol panel when playing audio.

If there is no sound on Intel Tiger Lake or newer platforms, they may need to load additional firmware file(s). These platforms likely need the [sys-firmware/sof-firmware](https://packages.gentoo.org/packages/sys-firmware/sof-firmware) package installed. Then, restart PulseAudio.

PulseAudio's user configuration files can become corrupt. Deleting \~/.pulse\* configuration files and forcing fresh ones to be generated by restarting the daemon may fix lack of sound.

If audio output has strange distortion or static, there's probably an issue with the Pulse server. Kill and restart the server:

`user $````
pulseaudio --kill
```
`user $````
pulseaudio --start
```
Sometimes adding `tsched=0` to the default.pa file in order to disable time scheduling may also work:

**`/etc/pulse/default.pa`**

On some *very* rare occasions, PulseAudio may need [reinstalling](https://wiki.gentoo.org/wiki/Emerge) in case of sound issues:

`root #``emerge --ask --oneshot pulseaudio`
To enable debug output, set `log-level` to `debug` in the /etc/pulse/daemon.conf:

**`/etc/pulse/daemon.conf`**

The daemon will then need to be restarted:

`user $``pulseaudio -k`
Problem: Out-of-sync problems experienced when using PulseAudio over a local network.

Solution: Add `tsched=0` to the default.pa file in order to disables time scheduling:

**`/etc/pulse/default.pa`**

Restart the daemon:

`user $````
pulseaudio --kill
```
`user $````
pulseaudio --start
```
If the only playback device is the **Dummy Output**, PulseAudio cannot access the system sound devices. Either the user has no permissions (refer to [the "Permissions" section of the "PulseAudio" page](https://wiki.gentoo.org/wiki/PulseAudio#Permissions), or another program is blocking access. In the latter case,

`user $``fuser -v /dev/snd/*`
should show which program is blocking access. Close that program and reconfigure it to use PulseAudio.

PulseAudio provides whatever latency is possible at any given moment. This can be from milliseconds to hundreds of milliseconds, without regard to what applications require.

If a buffer underrun occurs, PulseAudio buffers for longer latency, but then never tries to buffer for less until restart.

Re-sampling can require quite a lot of computational power. PulseAudio defaults are rather conservative, but in certain cases can still take a significant toll.

In such cases, edit /etc/pulse/daemon.conf and consider changing `resample-method` to something less CPU intensive. `default-sample-format` and `default-sample-rate` can also affect CPU utilization, with higher bit-depth and larger difference in sample-rate generally needing more resources (e.g. re-sampling 44.1 kHz to 48 kHz is faster than re-sampling either to 192 kHz). Since re-sampling is done per each channel per input, channel configuration and number of applications can affect performance as well.

Additionally, soxr resamplers can be made available by enabling the [sox](https://packages.gentoo.org/useflags/sox) [USE flag. In particular,](https://wiki.gentoo.org/wiki/USE_flag) `resample-method = soxr-mq` should provide acceptable quality, while even the higher quality (and hence slower) soxr-hq is still cheaper than the default speex-float-1. But be warned that the soxr resamplers have roughly 5-20 times higher latency than speex-float: in terms of time, the worst case for soxr-mq/hq can be as high as 20 ms, while soxr-vhq latency can, in a few specific setups, reach over 27 ms. In terms of perception, 20 ms can range from unnoticeable to irritating depending on person and use case (for comparison, the usual lower bound of PulseAudio's latency is around 20-25 ms, and more commonly around 70-90 ms).

Make sure the `CONFIG_GRKERNSEC_SYSFS_RESTRICT` kernel symbol is not enabled when using a grsecurity kernel. PulseAudio’s module-udev-detect needs to access /sys to discover what cards are available on the system, and that kernel option disallows this for anyone but root.

This may be caused by misbehaving PulseAudio-enabled programs when PulseAudio has *flat volumes* feature enabled. Disable it in the daemon config:

**`/etc/pulse/daemon.conf`**

```
flat-volumes = no
```
If changing the output device in pavucontrol has no effect, it could be an application using [media-libs/openal](https://packages.gentoo.org/packages/media-libs/openal), which has a configuration option that inhibits sink changes.

To disable this option, create a configuration file for OpenAL<sup>[\[2\]](https://wiki.gentoo.org#cite_note-2)</sup>:

![](https://wiki.gentoo.org/images/thumb/3/31/Alsoft-config.png/300px-Alsoft-config.png)

**`~/.config/alsoft.conf`**

```
[pulse]
allow-moves=yes
```
Or, from the GUI, by running :

`user $``alsoft-config`
PulseAudio hibernates when no sound is being played. A popping noise at boot, and each time sound is played, is due to PulseAudio (re)starting. One workaround is to disable hibernation in \~/.config/pulse/default.pa:

**`~/.config/pulse/default.pa`**
